# Credential audit

This page documents how major SQL clients store database credentials, with source code references where available.

The audit covers: DBeaver, DataGrip, TablePlus, pgAdmin, and Beekeeper Studio.

---

## Why credentials storage matters

A SQL client necessarily holds your database password. Where it stores that password determines what happens if:

- Your laptop is stolen (disk encryption aside)
- Another process on your machine reads your home directory
- A malicious npm package or browser extension gains filesystem access
- You accidentally push your home directory to a public repository

dbpeek stores **no credentials to disk**. Credentials are passed as CLI arguments and exist only in the Node.js process memory for the duration of the session. When you close the terminal, they are gone.

---

## DBeaver

DBeaver stores connection passwords in `~/.dbeaver/General/.dbeaver-data-sources.json`. In older versions, passwords were stored in plaintext. In current versions, they are obfuscated (not encrypted) using a hardcoded XOR key shipped with the application.

The key is public knowledge and several scripts exist to decode DBeaver credentials from the JSON file without needing DBeaver installed.

**Risk**: Any process that can read your home directory can recover all stored passwords trivially.

---

## DataGrip / IntelliJ database tools

DataGrip integrates with the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service) for password storage. This is the most secure approach among the tools audited.

However, passwords can optionally be stored in the project's `.idea/` directory (which is often committed to version control by accident) when the user selects "Remember in project" instead of "Remember in keychain".

**Risk**: Low when using OS keychain. High if project-level storage is used and `.idea/` is committed.

---

## TablePlus

TablePlus stores connection details (including passwords) in `~/Library/Application Support/com.tinyapp.TablePlus/Data/Connections.plist` on macOS, encrypted with AES-256.

The encryption key is derived from a machine-specific identifier, meaning:

- Credentials cannot be decrypted on another machine
- Any process running as the same user can access the encryption key from the same machine-specific source

**Risk**: Medium. Credentials are encrypted but the key derivation is deterministic and machine-local rather than user-provided.

---

## pgAdmin

pgAdmin stores the master password hash and connection credentials in an SQLite database at `~/.pgadmin/pgadmin4.db`. Individual passwords are encrypted with AES-256 using the master password as the key.

If no master password is set (the default in older versions), passwords are stored with a static key.

**Risk**: Low with a strong master password. High without one (static key encryption offers minimal protection).

---

## Beekeeper Studio

Beekeeper Studio stores connections in `~/.beekeeper-studio/app.db` (SQLite). Passwords are stored encrypted using the OS keychain on macOS and Linux (via `keytar`), with a fallback to an application-level key when the OS keychain is unavailable.

The community edition uses a weaker encryption fallback than the enterprise edition.

**Risk**: Low on macOS with keychain integration. Higher on Linux when the keychain is unavailable and the fallback key is used.

---

## Summary

| Client | Storage mechanism | Encrypted | Key source |
|--------|-------------------|-----------|------------|
| **dbpeek** | None (memory only) | N/A | N/A |
| DBeaver | JSON file in `~/.dbeaver/` | Obfuscated (XOR) | Hardcoded in app |
| DataGrip | OS keychain (or `.idea/`) | OS-managed | OS credential store |
| TablePlus | Plist in `~/Library/` | AES-256 | Machine identifier |
| pgAdmin | SQLite in `~/.pgadmin/` | AES-256 | Master password |
| Beekeeper Studio | SQLite + OS keychain | Varies | OS keychain or app key |
