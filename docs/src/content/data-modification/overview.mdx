# Data modification overview

<WarningCallout>All features in this section require `--write` or `--full` mode. The default read-only mode blocks all data modification. Pass the flag explicitly when starting dbpeek — for example, `npx dbpeek postgres://localhost/mydb --write`.</WarningCallout>

dbpeek ships with four data modification features, each gated behind an appropriate permission level.

## Permission modes

| Mode | Flag | What it allows |
|------|------|----------------|
| Read-only | *(default)* | SELECT, EXPLAIN, SHOW |
| Write | `--write` | All of the above + INSERT, UPDATE, DELETE, REPLACE, MERGE |
| Full | `--full` | All of the above + CREATE, DROP, ALTER, TRUNCATE, GRANT |

## Safety guarantees

Every modification feature follows the same safety pattern:

1. You initiate the change through the UI
2. dbpeek generates the SQL that would be executed
3. A **confirmation dialog** shows the exact SQL before anything runs
4. You click Execute to apply, or Cancel to discard

All modifications are logged to [query history](/analysis/query-history) with the same timestamp, status, and row-count information as regular queries.

## Transactions

Where possible, dbpeek wraps bulk modifications in a transaction:

- **CSV/JSON import** — all inserts run inside a single transaction. If any row fails, the entire import rolls back.
- **Table structure editor** — each ALTER TABLE is executed individually (databases generally don't support transactional DDL, except PostgreSQL which does).
- **Inline editing** — each UPDATE is a single-statement transaction by default.

For PostgreSQL specifically, DDL inside an explicit `BEGIN` / `COMMIT` block is transactional. The table editor takes advantage of this when possible.
